Guest exception dispatch is an error-path item (E5). Implementing it means running the `FS:[0]` handler chain with guest `EXCEPTION_RECORD`/`CONTEXT`, two-phase unwind through `RtlUnwind`, and finally the stored filter. It needs a reproducible guest trigger to validate, so it is not the next execution blocker for playable Training.

**Guest exception dispatch: implemented software path (2026-10-14).** A diagnostic C++ exception reaches either MFC's catch-all window-procedure frame or the CRT entry frame (`5AC586` -> `_except_handler3`). The supported implementation in `mfc_stage.hpp` follows this contract:
1. `RaiseException` service: build the guest `EXCEPTION_RECORD` and x86 `CONTEXT` below ESP. Walk `FS:[0]` (records validated inside the guest stack), calling each handler through `call_guest(record, frame, context, dispatcher)`. `ExceptionContinueSearch` moves to the next record. `ExceptionContinueExecution` returns from the service with the CONTEXT registers (allowed only if EIP is the return address and the exception is continuable). At the end of the chain, call the stored unhandled filter, then terminate with the exception code.
2. `RtlUnwind` service: call the handlers with `EXCEPTION_UNWINDING` up to the target registration, set `FS:[0]`, and return normally.
3. Lazy nonlocal return: the handler executes its lifted catch/continuation directly. When its eventual RET matches an outer bound return word and the supported restored ESP range, `returned()` throws `GuestReturn` carrying that frame index.
4. Catch by frame ownership: the owning `enter()` or `call_guest()` catches that frame index, restores the logical return depth and continues. Other host frames rethrow and unwind normally, releasing their resources. Unknown return words or unsupported ESP restores stop typed.
5. Lifted `__except`/`catch` targets: add scope-table handler addresses (and C++ EH funclets/continuations, if `_CxxThrowException` is reached) as closure roots, so the targets have bodies; a missing body stops typed.

Validation uses `MW34_SEH_TEST=1` to inject the same lifted `_CxxThrowException` call as MFC's `AfxThrowUserException`. `MW34_SEH_TEST_ANY=1` instead injects before the first game-code call and reaches the unhandled CRT path. These switches deliberately change behavior and are disabled in play profiles.

## Route decision: retail translated entry

The game's own CRT entry (`0x5AC3A0`, PE entry point) already runs natively through
five accepted service gates and the command-line producer, so the production host
follows that retail route instead of a host bootstrap that would skip it. A host
bootstrap would still have to reproduce every effect listed below; no evidence shows
it would remove a dependency. The remaining structural gap is that every native
chain still starts from **captured original BEFORE state** (provider DLL attach and
process state). Replacing that seed with host-built, contract-equivalent provider
state is the integration work of E1, not a reason to bypass translated entry.
